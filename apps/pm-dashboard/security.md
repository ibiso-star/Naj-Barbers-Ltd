# Security — Keel

> Generated by scripts/split-charter.py from PRD.md sections 8.1 (security baseline), 8.7 (deployment & operations), and 8.8 (incident response) — the controls that keep this project safe to run and recoverable, not just safe to ship once.

### 8.1 Security baseline

**Auth, sessions & access control**
- [x] 🔴 [SEC-001] Auth/authorization checks enforced server-side on every protected route — the UI is never the security boundary. A blur is not a paywall, a hidden button is not a permission gate, a disabled field that reached the browser is already visible in the network tab. Client-side hiding is a nice trick on top of a real server-side gate, never instead of one.
- [ ] 🔴 [SEC-002] Session tokens never stored in `localStorage` (XSS-readable) — use httpOnly cookies
- [x] 🔴 [SEC-003] IDOR protection: never trust an ID that came from the client; verify per-object ownership server-side on every request; prefer a public nickname/UUID over exposing sequential internal IDs — **but note UUIDs are defense-in-depth, not a substitute for the actual server-side authorization check**
- [x] 🔴 [SEC-004] Mass-assignment protection: explicitly allow-list which fields a client can set on create/update (a signup request must never be able to set its own role/privilege/ownership fields)
- [ ] 🔴 [SEC-005] If custom admin/staff functions exist, require MFA for privileged accounts and enforce server-side authorization for every privileged action; hiding or renaming an admin URL is not an access control
- [ ] 🟡 [SEC-006] Access token + refresh token separation, with proper handling of mid-flow token expiry; refresh tokens must be force-revocable without unnecessarily logging the user out everywhere
- [ ] 🟡 [SEC-007] Sessions invalidated on password change; password-reset links expire
- [ ] 🟡 [SEC-008] Adaptive abuse protection on login: per-IP/per-account rate limiting with progressive backoff and risk-based step-up challenges (CAPTCHA only when actually justified by risk signals) — **do not rely on a hard account lockout as the sole defense; a flat lockout lets an attacker deliberately lock out a victim**
- [ ] 🟡 [SEC-009] User enumeration prevented (login/signup/reset flows don't reveal whether an email/username exists)
- [ ] 🟡 [SEC-010] *(If the project uses password-based auth at all)* Password rules enforced two ways: client-side for UX feedback, and a server-side breached-password screening check as the real gate. If auth is passwordless/social-only, mark N/A.
- [ ] 🟢 [SEC-011] 2FA/OTP available
- [ ] 🔴 [SEC-012] An in-app/web deletion path fulfils the applicable platform and data-protection requirements: delete or anonymise data unless a documented legal, contractual, fraud-prevention, security, or tax-retention obligation requires restricted retention; clearly tell the user what remains and why — this is a 🔴 in section 9 only because Apple demands it for mobile, but it's the same user right on web, driven by data-protection law rather than a store policy

**Input, data & injection**
- [x] 🔴 [SEC-013] All user input is validated server-side against an allow-listed schema before use or storage — never trust client-side validation alone. Apply context-appropriate output encoding on render; sanitise only formats that need it (e.g. permitted rich HTML), rather than altering all stored data indiscriminately — blanket sanitization-at-write is a known anti-pattern that corrupts legitimate data and doesn't reliably prevent XSS on its own
- [x] 🔴 [SEC-014] SQL injection / XSS / CSRF protections verified, not assumed from framework defaults (CSRF tokens matter for cookie-based session auth specifically; a Bearer-token API has a different risk profile — apply the right control for the actual auth mechanism, not both blindly)
- [ ] 🔴 [SEC-015] File uploads validated by allow-listed type/size, never trusted as-is
- [ ] 🔴 [SEC-016] Prices, quantities, and anything financial always computed/verified server-side — never trust a client-submitted price
- [ ] 🟡 [SEC-017] Request body size limits enforced

**Secrets, dependencies & supply chain**
- [x] 🔴 [SEC-018] No secrets, API keys, or credentials committed to the repo — ever, including in commit history
- [x] 🔴 [SEC-019] Tokens/passwords/credentials scrubbed from application logs
- [x] 🔴 [SEC-020] Secrets managed via a proper secrets manager/env config, never hardcoded
- [ ] 🟡 [SEC-021] Secrets rotated periodically and immediately on suspected compromise
- [ ] 🟡 [SEC-022] GitHub Actions and other CI steps pinned to commit hashes, not mutable version tags
- [ ] 🟡 [SEC-023] Subresource Integrity (SRI) hashes on third-party `<script>` tags that are stable enough to maintain a fixed hash; skip for scripts that update too frequently for SRI to be practical
- [x] 🟡 [SEC-024] Source maps never **publicly** exposed — uploading them privately to your error-monitoring tool (e.g. Sentry) for readable stack traces is fine and encouraged; shipping them to the public build is what to avoid
- [ ] 🟡 [SEC-025] Dependency vulnerabilities checked before launch and on a recurring schedule after
- [x] 🟡 [SEC-026] Lockfiles committed and installs are deterministic (`package-lock.json`/`pnpm-lock.yaml`/`poetry.lock` etc.) — pinning CI actions and adding SRI doesn't help if the dependency tree itself still floats

**Network & infra**
- [ ] 🔴 [SEC-027] HTTPS/TLS enforced everywhere, no mixed content
- [ ] 🔴 [SEC-028] Encryption at rest for the database, backups, and file storage — TLS covers data in transit only; backups in particular are the classic thing left unencrypted and forgotten
- [ ] 🔴 [SEC-029] Least-privilege IAM roles and DB permissions — no wildcard access "to make it work"; this extends to service-to-service auth between containers, not just the database
- [ ] 🔴 [SEC-030] Abuse controls are defined and enforced for public attack surfaces, especially auth, password-reset, search/expensive operations, payment, upload, and state-changing routes — document actual thresholds, the identity key used (IP/account/device), response behavior, and any exceptions for legitimate traffic, not just "rate limiting exists"
- [ ] 🟡 [SEC-031] CORS locked down to known origins
- [ ] 🟡 [SEC-032] HSTS enabled — do this once HTTPS is verified across the full domain/subdomain inventory; enabling HSTS (especially with preload) before every subdomain is HTTPS-ready can lock you into a hard-to-reverse state
- [ ] 🟢 [SEC-033] Directory listing disabled where the hosting platform doesn't already prevent it by default (check whether this even applies to your platform before treating it as a gap)
- [ ] 🟡 [SEC-034] CDN must never cache user-specific/personalized pages
- [ ] 🟡 [SEC-035] Payment/webhook handlers verify signatures **and** reject replayed or stale requests, not just check that the signature is valid
- [ ] 🟢 [SEC-036] Idempotency keys on critical state-changing endpoints (payments, order creation) — generalizes webhook-replay protection to any critical mutation, not just webhooks

**AI/agent-specific**
- [ ] 🔴 [SEC-037] Prompt-injection controls are designed per trust boundary wherever user-controlled or external content reaches an LLM, an agent, a retrieval pipeline, a tool call, or an automated action — not just a chat input box: treat external content as untrusted, use least-privilege scoped tools and allow-lists, require confirmation for consequential actions, and record the test cases/evidence
- [ ] 🔴 [SEC-038] AI-generated code/actions are reviewed or executed in an appropriately isolated sandbox before any filesystem, network, payment, or other consequential side effect — never auto-trusted as if it were already-vetted input
- [ ] 🟡 [SEC-039] AI usage capped two ways: a hard cost/budget ceiling *and* a per-user rate limit — not just one number

**Operational**
- [ ] 🟡 [SEC-040] Security events logged (auth attempts, rate-limit trips, etc.)
- [ ] 🟡 [SEC-041] Audit trail for privileged actions — who-changed-what on admin actions is a different capability from auth-event logging above, and it's specifically what you need during an incident
- [ ] 🟡 [SEC-042] Secure cookie flags set (httpOnly, secure, sameSite)


### 8.7 Deployment & operations
- [ ] 🔴 [OPS-001] Staging environment exists and is used before anything reaches production — and staging never contains real production personal data; copying prod to staging is one of the most common accidental breaches there is
- [ ] 🔴 [OPS-002] Monitoring/alerting configured for errors and downtime (Sentry + basic infra alerts at minimum)
- [ ] 🔴 [OPS-003] Automated database backups configured **and the restore has actually been tested** — a backup that has never been restored is a guess, not a backup
- [ ] 🟡 [OPS-004] Rollback plan exists and has actually been considered
- [ ] 🟡 [OPS-005] Domain/subdomain strategy decided deliberately (e.g. `app.` vs. a separate domain), not defaulted
- [ ] 🟡 [OPS-006] Email authentication configured (SPF/DKIM/DMARC) for the sending domain — without this, password-reset and transactional email land in spam, which is both a security and a support problem
- [ ] 🟡 [OPS-007] Confirm whether the project is statically or dynamically hosted — a non-statically-hosted (server-rendered/dynamic) site needs the full server-side security checklist applied (session handling, auth checks, etc.); don't assume a static site's lighter risk profile for a dynamic app
- [ ] 🟢 [OPS-008] Standard operational email addresses set up as needed: `ops@`, `marketing@`, `no-reply@`, password-reset sender identity


### 8.8 Incident response
- [ ] 🟡 [IR-001] A named owner for security/production incidents exists (even if it's just you right now)
- [ ] 🟡 [IR-002] Escalation path documented — who gets pulled in and how, at 2am if needed
- [ ] 🟡 [IR-003] Recovery objectives stated: how much data loss is tolerable (RPO), how long can it be down (RTO)
- [ ] 🟡 [IR-004] Credential-rotation step included in the incident playbook (rotate first, investigate second, if a leak is suspected)
- [ ] 🟢 [IR-005] Containment steps documented (how to pull a compromised service/key out of production fast)
- [ ] 🟢 [IR-006] Post-incident review expected after anything real happens — not to assign blame, to fix the gap
