## 6. Architecture & Trust Boundaries `[EDIT PER PROJECT]`

- **System diagram or written description:** Next.js App Router frontend (server components for the shell and workspace membership check; client components for the interactive board) talking to Supabase: Postgres with RLS via PostgREST, Supabase Auth (magic link, cookie sessions via @supabase/ssr), and Supabase Realtime (postgres_changes on tasks, projects, subtasks and task_activity filtered by workspace_id). A repository interface isolates the UI from the data source; a browser-local demo repository implements the same interface for offline demos
- **Flow diagram link:** `docs/flows.md` (Mermaid diagram in the repo; no FigJam file per the owner's code-is-the-design-artifact convention) — the actual FigJam/diagram covering clients, services, databases, third-party providers, and where secrets live; don't just describe it in prose
- **Trust boundaries:** (1) Browser → Supabase PostgREST/Realtime: the user's JWT is the only credential; RLS re-checks workspace membership and role on every row; column-level grants and CHECK constraints restrict what clients may write. (2) Browser → Next.js server: the server reads the session cookie and verifies membership before rendering a workspace shell. (3) Database triggers → task_activity: written as the definer, not trusted from the client. The service-role key is never shipped to the browser and is not used by this app — every place data crosses from one trust level to another (client → server, server → third-party API, service → service) is a place authorization must be re-checked, not assumed

### 7.1 Repository Structure `[EDIT PER PROJECT — Reference Layout below]`

AI coding agents produce dramatically more maintainable output when given a structure
to build inside rather than a blank repository to organize however the moment
suggests. This subsection exists so that decision gets made once, here, rather than
re-decided — differently — every session an agent touches the codebase.

**Reference layout, for the default stack above** — one monorepo, not separate
repositories for frontend and backend:

```text
Keel/
├── apps/
│   └── web/                    # Next.js frontend
├── services/
│   └── api/                    # FastAPI backend
├── packages/
│   └── api-contracts/          # Generated OpenAPI TS types/client — the only
│                                 sanctioned way the frontend learns API shapes
├── infra/
│   └── terraform/               # AWS infrastructure as code
├── docs/
├── scripts/
├── .github/workflows/
├── docker-compose.yml            # local dependencies only
├── .env.example                  # see templates/env.example
├── .gitignore                    # see templates/gitignore.example
├── AGENTS.md                     # see below — required, not optional
├── CLAUDE.md                     # thin pointer to AGENTS.md, for Claude Code
└── README.md
```

Deviate from this layout under the same rule as the stack itself: state the reason,
don't silently reorganize.

**Backend layering — every FastAPI service in `services/api` follows this, no
exceptions:**

| Layer | Responsibility | Must not do |
|---|---|---|
| `api/v1/*.py` (routes) | Receive the HTTP request, call one service method, return its result | Contain business logic or raw SQL |
| `schemas/` | Validate request/response shape (Pydantic) | Double as the database model |
| `services/` | Business rules, workflows, orchestration | Know about HTTP (status codes, headers) |
| `repositories/` | Database reads/writes only | Call a third-party API (Stripe, OpenAI, S3) |
| `models/` | SQLAlchemy table mapping | Be returned directly as an API response |
| `integrations/` | Vendor SDK clients (Stripe, OpenAI, S3, Resend) | Make authorization decisions |
| `workers/` | Long-running async jobs (SQS-triggered) | Handle a live browser request |

A request therefore always flows one direction — `route → service → repository →
database` — and the response is a `schemas/` object the service builds, never a raw
model or raw query result handed back through the route. This isn't new engineering
doctrine: it's what makes the migration/query-hygiene rules already in 8.3 and the
trust-boundary rule in section 6 actually enforceable in practice, rather than
aspirational. "Service must not know about HTTP" and "route must not touch the
database" are this document's existing authorization/trust-boundary requirements,
structurally forced instead of merely stated.

**Frontend — feature folders, not type folders, beyond the shared primitives:**

```text
apps/web/src/
├── app/                  # routes only (Next.js App Router)
├── components/ui/         # generic, reusable, brand-agnostic primitives only
├── features/<feature>/    # everything specific to one feature lives together
│   ├── api.ts             # calls packages/api-contracts's generated client —
│   │                         never a raw fetch to a hand-typed endpoint
│   ├── schemas.ts
│   ├── hooks/
│   └── components/
└── lib/                   # cross-feature utilities (auth helpers, the
                              configured API client itself)
```

**Required: every project's repository root carries an `AGENTS.md`** (or the
coding-agent-equivalent file for whichever tool is in use) restating this section's
layout and layering rules as standing instructions, with links to sections 6 and 8 for
the trust-boundary and security rules that apply to every change. This is not a
duplicate of section 14 — section 14 governs how an agent should behave *when handed
this document in a live session*; this file is what governs any agent touching the
repo on a later, unrelated session that never saw this document at all. One is a

- [ ] 🟡 [ARCH-002] A new feature's PR/commit doesn't introduce a second, competing structure (e.g. business logic inside a route handler) without that being caught in review

### 7.2 Build Order & Communication Model `[EDIT PER PROJECT — Reference Order below]`

Section 7.1 defines where code lives; this defines what order it gets built in and how
the pieces are allowed to talk to each other. Skipping this order is what produces a
frontend built against a guessed API shape that drifts from what the backend actually
returns.

**Reference build order, for a new feature or a new project's first feature:**

1. **Data model & migration** — the entities from section 5, as an actual Alembic
   migration against a real (even if empty) database. Not a guess at what the schema
   will probably look like.
2. **Repository + model** — the actual queries, against the actual migrated schema.
3. **Service** — the business logic, calling the repository, still with no HTTP
   awareness.
4. **Route + schema** — the thin HTTP layer, wired to the service, its request/response
   shape captured as an OpenAPI schema.
5. **Generated client** — `packages/api-contracts` regenerated from that OpenAPI
   schema.
6. **Frontend feature** — built against the generated client from step 5, never
   against a hand-typed guess of what the endpoint returns.

Building frontend and backend for the same feature in parallel from a shared guess is
how the two drift; building in this order means the frontend literally cannot compile
against an API shape that doesn't exist yet.

**Communication model** — restated explicitly, not left implicit in the folder layout
alone:

```text
Next.js frontend
      │  HTTPS + auth (see section 6 trust boundaries)
      ▼
FastAPI backend
      │
      ├── PostgreSQL / RDS
      ├── Redis / ElastiCache
      ├── S3
      ├── SQS
      └── LLM providers
             │
             ▼
      ECS worker containers
```

- [ ] 🔴 [ARCH-003] The frontend never connects to Postgres, Redis, SQS, or any vendor secret
      directly — every one of those is reached only through the FastAPI backend, over
      the same authenticated API the frontend already uses for everything else
- [ ] 🟡 [ARCH-004] The frontend knows API endpoints and response *types* (via the generated
      client); it does not know database table names, raw SQL, queue configuration, or
      any backend-only credential — if a frontend file needs to know one of those to
      work, that's a layering violation, not a convenience

## Keel as built `[PROJECT-SPECIFIC — supersedes the reference layout above]`

The reference layout and FastAPI layering above don't apply. There's no
backend service; see `decisions.md` D-001/D-002. This is the layout agents
must follow:

```text
apps/pm-dashboard/
├── src/
│   ├── app/                     # routes only (App Router)
│   │   ├── w/[workspace]/       # server layout = membership gate; one page per view
│   │   ├── login/ auth/ onboarding/
│   │   └── globals.css          # design tokens (PRD.md §3)
│   ├── proxy.ts                 # Supabase session refresh only; no authorisation
│   ├── components/ui/           # brand-agnostic primitives (Button, Modal/Drawer, Field, Popover…)
│   ├── features/<feature>/      # overview, tasks, projects, team, settings, shell, workspace
│   └── lib/
│       ├── data/                # the ONLY place that knows table/column names
│       │   ├── repository.ts    # interface the UI depends on
│       │   ├── supabase-repository.ts / demo-repository.ts
│       │   ├── schemas.ts       # zod allow-lists mirroring the column grants
│       │   ├── database.types.ts, mappers.ts, seed.ts
│       ├── metrics.ts, tasks/   # pure logic, unit-tested
│       └── supabase/            # client factories
├── supabase/
│   ├── migrations/0001_init.sql # schema, RLS, grants, triggers, realtime publication
│   ├── seed.sql                 # GENERATED from src/lib/data/seed.ts
│   └── tests/                   # auth stub + RLS/grant/trigger assertions
├── e2e/                         # Playwright journeys + axe scans
└── scripts/                     # standards tooling, generate-seed.mts, test-db.sh
```

**Layering rules (the equivalent of the backend table above):**

| Layer | Responsibility | Must not do |
|---|---|---|
| `app/**/page.tsx` | Read route params, render one feature view | Fetch data or hold business logic |
| `app/w/[workspace]/layout.tsx` | Server-side membership check under RLS (SEC-001) | Trust anything from the client |
| `features/*` components | Render and call `useWorkspace()` actions | Import `supabase-js`, name a table, or build a query |
| `features/workspace/WorkspaceProvider` | Optimistic state, realtime, rollback and toasts | Decide authorisation |
| `lib/data/*-repository.ts` | Talk to the data source; map rows to domain types | Be imported by components directly (the shell's workspace creation is the one exception) |
| `supabase/migrations` | **The authorisation layer**: RLS, grants, CHECKs, triggers | Rely on the client filtering by workspace |

**Build order used:** migration → RLS tests against real Postgres → domain
types and mappers → repositories → store → UI. That's the §7.2 order with
PostgREST standing in for the route/schema/client steps.

**CI sequence** (`.github/workflows/ci.yml`, job `pm-dashboard`): lint →
typecheck → unit → seed-sync → database tests → build → E2E and axe. A
separate job runs the charter build check.
